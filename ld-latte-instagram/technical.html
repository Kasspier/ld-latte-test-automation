01

Выбор подключения и границы проекта

Цель: получать подписчиков, просмотры, охват и результаты собственных публикаций нескольких аккаунтов в общей отчётности. Основной маршрут — Instagram API with Unified Login, рекомендованный Meta для новых интеграций. Вызовы — через graph.facebook.com; в просмотренной справке актуальна версия v27.0. Версию фиксируем в настройках и проверяем перед обновлением.

Предварительные условия: профессиональные профили Business/Creator, доступ владельца к их бизнес-портфолио, корпоративное приложение Meta в портфолио компании, администратор приложения, Facebook Login for Business, HTTPS callback и подготовка webhook endpoint по руководству Meta. Аккаунты не связываются друг с другом. Для Page-based Facebook Login каждый связан со своей Facebook Page; для Unified Login Page не обязательна.

План, который можно передать специалисту

В рамках задания не создаём приложение Meta, не получаем токены и не обращаемся к реальным аккаунтам. Примеры запросов ниже — шаблоны внедрения, а не результаты выполненной интеграции.

02

Права, роли и жизненный цикл токена

Настройка прав основного маршрута

В Use cases → Manage messaging & content on Instagram → Customize → API setup with unified login создаём конфигурацию и сохраняем config_id. Мастер по умолчанию включает также публикацию, комментарии и рекламу. Убираем необязательные права и рекламные объекты, добавляем instagram_manage_insights. В текущем руководстве instagram_basic и instagram_manage_messages обязательны для создаваемой конфигурации: нельзя обещать владельцу исключительно read-only согласие.

Если компания не согласна на обязательное право сообщений, выбираем Instagram Login с двумя аналитическими scopes. Право business_management нужно для Business Integration System User Access Token Management API; добавляем его только при выборе этого способа сопровождения и отдельно объясняем владельцу. Не используем права публикации или рекламы в сборщике статистики.

Для пилота назначаем администратору/разработчику роль в приложении, приглашаем настоящий профессиональный тестовый аккаунт и принимаем приглашение. Синтетические test users этим руководством не поддерживаются. Стандартного доступа достаточно для соответствующих собственных/управляемых аккаунтов с ролями. Для внешних пользователей — Live mode, Advanced Access для каждого запрашиваемого права, App Review и необходимое подтверждение компании. Успех у администратора ещё не доказывает доступ у клиента без роли.

Хранение и отзыв

Токены и App Secret — только в серверном хранилище секретов, шифрование при хранении, доступ только сборщику. В базе аккаунтов — ссылка на секрет. Не включаем значения в HTML, BI, git, логи и уведомления. В запросах данных предпочитаем заголовок Bearer; параметры обмена, которые требует OAuth endpoint, маскируем в серверных журналах. Токен может быть отозван раньше срока. При удалении интеграции или переносе профиля в другое портфолио останавливаем затронутое подключение и просим владельца пройти вход заново. Уже сохранённые показатели не затираем.

Основание: настройка [2], SUAT [3], права [4], Instagram OAuth [9], диагностика [11]. Сроки и расписание контроля выше разделены: свойства API и предлагаемый регламент компании.

03

От исходного аккаунта до первого запроса

Владелец готовит профили и выбирает портфолио/аккаунты. Специалист настраивает конфигурацию, права и точный HTTPS redirect URI. Сервер создаёт одноразовый state, связывает его с сессией подключения, проверяет на callback и сразу обменивает code. Отмену согласия обрабатываем как отмену, без попыток создать пустое подключение.

01 · Владелец → Meta

Вход по config_id. Выбор портфолио и нескольких IG. Проверка согласия.

02 · Meta → Сервер

Callback: code + state. Проверка state. Серверный обмен на SUAT.

03 · Сервер → Graph API

client_business_id и assigned_instagram_accounts. Проверка всех страниц списка.

04 · Graph API → Сборщик

Профиль, subscribers, reach и views пилота. Отдельно статистика одной публикации.

05 · Сборщик → База

Нормализация, период, единицы и статус. Запись без дублей.

06 · База → Отчёт

Сверка маркетологом. Дата обновления. Подключение остальных профилей и расписание.

1. Ссылка согласия

https://www.facebook.com/dialog/oauth?
  client_id=<META_APP_ID>&config_id=<CONFIG_ID>
  &redirect_uri=<URL_ENCODED_HTTPS_CALLBACK>
  &response_type=code&prompt=login&state=<ONE_TIME_RANDOM_STATE>

2. Обмен на сервере

Согласно текущему руководству Unified Login: GET https://graph.facebook.com/v27.0/oauth/access_token, параметры client_id, client_secret, code. Секрет не попадает в браузер. Проверяем соответствие redirect URI конфигурации и требованиям выбранного OAuth-потока; пример руководства Meta опускает этот параметр обмена. Код не переиспользуем.

3. Определение бизнеса и аккаунтов

GET https://graph.facebook.com/v27.0/me?fields=client_business_id
Authorization: Bearer <SUAT>

GET https://graph.facebook.com/v27.0/me/assigned_instagram_accounts?fields=id,username
Authorization: Bearer <SUAT>

В Unified Login /me — системный пользователь, а не Instagram-профиль. Сохраняем полученный business ID и каждый выбранный IG ID как строку. Для следующего запроса берём конкретный ID из assigned_instagram_accounts; не подставляем /me и не вычисляем его по username.

4. Профиль и первая статистика

GET https://graph.facebook.com/v27.0/<IG_ID>?fields=id,username,followers_count
Authorization: Bearer <SUAT>

GET https://graph.facebook.com/v27.0/<IG_ID>/insights?metric=reach,views&period=day&metric_type=total_value&since=<UNIX_START>&until=<UNIX_END>
Authorization: Bearer <SUAT>

GET https://graph.facebook.com/v27.0/<IG_ID>/media?fields=id,media_type,media_product_type,timestamp,permalink
Authorization: Bearer <SUAT>

GET https://graph.facebook.com/v27.0/<MEDIA_ID>/insights?metric=views,reach
Authorization: Bearer <SUAT>

UNIX_START/END задаём явно для одного завершённого дня в согласованной зоне; сохраняем фактические границы. Справка описывает включённые границы since/until: не предполагаем автоматически полуоткрытый интервал; проверяем границу на пилоте. Для публикации это lifetime, не статистика выбранных суток. Затем пробуем допустимые метрики её формата. Нормализатор читает как total_value.value, так и values[].value, проверяет имя и период. Пустой data — «нет данных», не ноль. Успех подтверждается валидным ответом нужного объекта и сверкой, а не только HTTP 200.

Порядок и запросы: Get Started [2], Account Insights [7], Media Insights [8], IG User [10]. Это шаблоны; реальные ответы не получены по условиям задания.

Общие ограничения

Статистика относится к разрешённым профессиональным аккаунтам и их контенту; данные до перехода в профессиональный тип могут быть недоступны. Расчёт может запаздывать до 48 часов. Наличие 90 дней истории аккаунта не означает, что весь диапазон доступен для каждой метрики и одного запроса. Глубину первичной загрузки проверяем на пилоте и запрашиваем совместимыми окнами. Демографию и online_followers не включаем в обязательный набор: у них дополнительные пороги/периоды.

Основание: Insights [6], аккаунт [7], медиа [8], профиль [10]. Если примеры общего руководства расходятся с таблицей endpoint, используем текущую справку endpoint и подтверждаем пилотом.

05

Несколько аккаунтов и регулярное сохранение

Предлагаемый стек реализации: n8n как планировщик и HTTP-сборщик → PostgreSQL → текущая BI-система или таблица компании. Это архитектурное предложение, не обязательный стек из ТЗ. OAuth callback и хранилище секретов размещаются на сервере под контролем компании. Отчёт не получает токены.

Каждое бизнес-портфолио имеет отдельное подключение; несколько разрешённых аккаунтов одного портфолио могут использовать один SUAT. Очередь обрабатывает каждый IG ID отдельно, с ограничением параллельности и блокировкой одновременных запусков для одного аккаунта. Смена username не создаёт новый аккаунт; ключ — стабильный IG ID вместе с конфигурацией/подключением.

Предлагаемый регламент

  • Ежедневно: subscribers сейчас; reach/views за завершённый день. Повторно загружаем последние 3 дня из-за задержки расчёта. Первичная история аккаунта — в доступном диапазоне до 90 дней по каждой метрике.
  • Публикации: находим новые, обновляем свежие чаще, старые реже. Храним lifetime-снимки с датой. Изменение между снимками не выдаём за официальную суточную метрику.
  • Stories: опрос каждые 1–3 часа, если включены в объём; только свежие объекты, без обещания полной старой истории.
  • Надёжность: временные сетевые/5xx ошибки и лимиты — ограниченные повторы с exponential backoff и jitter, с учётом Retry-After и usage-заголовков Meta. Ошибки прав и параметров бесконечно не повторяем. Сбой одного аккаунта не прерывает другие.
  • Данные: UTC в хранилище, согласованный бизнес-часовой пояс в отчёте. Сохраняем определения и единицы. Нормализованные данные и безопасный исходный payload помогают сверке; URL из paging с токеном в логи не пишем. «Нет данных» хранится статусом с NULL; настоящий 0 остаётся нулём.
  • Мониторинг: показываем last_success_at и пропуски. Предлагаемый порог — уведомление, если ежедневная загрузка не завершилась в течение суток после согласованного времени. Канал уведомлений и допустимую задержку утверждает компания.

Срок хранения в собственной базе, доступ сотрудников, удаление при отключении и резервные копии согласуются с компанией и правилами Meta. Сохранённая история не зависит от повторной доступности того же периода в API. Расписание адаптируем под количество аккаунтов и фактические лимиты; фиксированную универсальную квоту запросов не обещаем.

Ошибка callback или обмена codeСовпадение redirect URI, App ID/Secret правильного типа, state, свежесть и однократность code.Исправить настройку; начать новый вход. Не записывать code/secret в журналы.
Недействительный токен / OAuth code 190Срок, отзыв, перенос профиля, соответствие app/host/login_type. Помощник Instagram может не понимать SUAT.Для SUAT проверить прямым запросом нужного объекта. При отзыве/переносе остановить подключение и переподключить; исключить бесконечные повторы.
Code 10/200: нет доступаТекст и subcode ошибки, выданные scopes, Advanced Access, Live mode, роли, professional type, право на объект.Сравнить с таблицей требований endpoint. Получить новое согласие при добавлении прав. Один code 10 сам по себе не определяет причину.
Code 10: Not enough viewersФормат STORY и конкретное сообщение о пороге зрителей.Сохранить статус недостаточно данных; не считать это автоматически потерей всех прав или нулём просмотров.
Пустой data / нет метрики / code 100Поддержка metric, period, metric_type и breakdown для формата; даты, размер окна, возраст контента, пороги аудитории.Разделить несовместимые запросы; повторить свежие данные позже; недоступность отмечать явно. Не заменять нулями.
429 / rate-limit ошибка Graph / 5xxHTTP и Graph error, usage-заголовки, параллельность, повторы/дубли планировщика.Снизить нагрузку, ограничить очередь, backoff. После максимума попыток уведомить и сохранить checkpoint.
Цифры отличаются от InstagramДаты/UTC, дата сбора, органика/реклама, IG/Facebook, lifetime/день, задержка 48 часов, приблизительный reach.Согласовать одинаковые определения; перечитать окно. Не исправлять числа вручную ради совпадения.
Пилот работает, клиент не подключаетсяРоль администратора могла скрыть отсутствие Advanced Access.Проверить Live mode и одобрение всех фактически запрашиваемых scopes; после approval протестировать пользователя без роли.

Для поддержки фиксируем app_id, config_id, этап, безопасный ID объекта, время с зоной, код/subcode, fbtrace_id и сообщение без секретов. Пароли, токены, App Secret и полный OAuth URL не прикладываем. Ответственный за доступ — владелец; за повтор и техническое исправление — специалист.

Основные причины подключения: официальная диагностика [11]. Проверки метрик: [7], [8]. Retry и журналирование — проектные решения.

План проверки и соответствие заданию

Ниже будущая приёмка интеграции. В этом тестовом задании проверяется полнота плана; реальные аккаунты и токены не запрашивались.

Этап / исполнительПроверкаКритерий успеха
Подготовка · владелец + специалистСверить реестр профилей, professional type, портфолио, роли, корпоративное приложение.Каждый аккаунт имеет ответственного и понятный маршрут подключения.
Согласие · владелецПроверить config_id, выбранные объекты и scopes, в том числе обязательное messages; отказ/отмена.Нет несогласованных объектов и прав. При отмене подключение не создаётся.
