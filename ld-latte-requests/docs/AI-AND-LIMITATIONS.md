# AI-инструменты и ограничения

## Как использовался AI

Codex помог спроектировать Next.js-приложение, написать Route Handlers, React-интерфейс, SQL-миграцию, Postman-коллекцию и документацию. Требования ограничены задачей №3: AI-функций внутри сервиса нет.

Результат проверялся компилятором TypeScript, production-сборкой Next.js, тестами валидации и границы API, исполнением миграции и RLS на локальном PostgreSQL, а также HTTP smoke-прогоном Postman-коллекции.

В браузере проверены экран первого подключения, вход, заполненный список, создание/изменение заявки, мобильная форма и изоляция двух пользователей с настоящими сессиями Supabase.

## Что пришлось уточнить и исправить

- Supabase вернул `over_email_send_rate_limit` при отправке писем подтверждения. Сообщение «Лимит регистраций» заменено точным описанием почтового лимита. Приложение также различает ограничения получателей встроенного почтового сервиса, отклонённые адреса и частоту запросов. Настройки подтверждения почты автоматически не меняются.

- Во время регистрации через `127.0.0.1` Next.js передавал внутренний URL с `localhost`, из-за чего проверка Origin ошибочно возвращала 403. Сравнение исправлено на фактический Host при сохранении проверки протокола и порта; добавлены тесты на допустимый адрес и запрещённые чужие origins.

- Первоначальная вставка явно передавала `status`, хотя права INSERT намеренно не разрешают пользователю задавать начальный статус. Вставка исправлена: `Новая` назначается базой.
- Проверка Content-Type сделана точной, чтобы похожая строка вроде `application/json-malicious` не проходила.
- Ограничение тела проверяет реальные байты потока, а не только недоверенный Content-Length.
- Windows-песочница блокировала rename в кеше тестов и соединения к локальному серверу. Проверки повторены вне этих ограничений; это не считалось падением бизнес-логики.
- В Newman 6.2.3 аудит обнаружил уязвимые транзитивные пакеты. После smoke-прогона Newman удалён из проекта; тесты поставляются как импортируемая Postman-коллекция и поддерживают отдельный Postman CLI.

## Состояние облачного подключения

Supabase `Test LD LATTE` подключён. Таблица и RLS созданы миграцией; публичное выполнение служебной `rls_auto_enable()` закрыто второй миграцией. Проверка Security Advisor после миграций не показала предупреждений. По явному решению пользователя подтверждение почты временно выключено в тестовом проекте, что проверено через `/auth/v1/settings`.

При включённой почтовой отправке регистрация фиктивного адреса `example.com` отклонялась Supabase (`email_address_invalid`). Прямое создание пользователей в служебных Auth-таблицах не выполнялось. После отключения Confirm email два тестовых аккаунта созданы обычным signup API; полный Postman-прогон завершён без ошибок: 50 запросов и 107 проверок.

## Что остаётся проверить

- SMTP и весь сценарий писем подтверждения после обратного включения Confirm email.
- Отдельный сценарий медленной/обрывающейся сети в браузере и восстановления после истечения долгой cookie-сессии. Блокировка кнопок во время сохранения и повторная отправка одного UUID проверены.
- HTTPS-хостинг проверен на Vercel; доступ к приватному GitHub выдаётся приглашением, когда известен проверяющий.

## Ограничения текущего MVP

- Администрирование, удаление заявок, вложения, уведомления и AI-генерация не входят в ТЗ.
- При одновременном редактировании действует последнее сохранение.
- Дедупликация относится к одному UUID: две отдельные формы могут создать одинаковые по смыслу заявки.
- Bearer access token после выхода может действовать до своего срока истечения; отдельного blacklist JWT нет.
- Supabase применяет свои лимиты Auth; дополнительного распределённого rate limiter на уровне Next.js нет.
- При отключённом интернете серверные операции недоступны; локального офлайн-хранилища заявок нет.
- Без SQL-миграции авторизация может работать, а запросы к таблице будут возвращать ошибку. Нужно выполнить все шаги README.
- Confirm email выключен только для тестирования; владение почтовым адресом не проверяется. Перед публичным запуском нужно настроить SMTP, включить подтверждение и отдельно решить судьбу созданных без подтверждения аккаунтов.
