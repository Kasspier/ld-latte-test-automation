## Автоматические тесты

```powershell
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
```

| Файл                        | Что проверяет                                                                                                                                         |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tests/domain.test.ts`      | Обязательные поля, длины, категории, статусы, UUID, запрет лишних полей/подмены владельца, параметры списка, экранирование поиска                     |
| `tests/api.test.ts`         | Same-origin записи, Content-Type, битый JSON, фактический размер тела, безопасный формат ошибок, отсутствие кеширования                               |
| `tests/database.test.ts`    | Применение настоящей SQL-миграции, дефолты, права колонок, RLS, изоляция А/Б, запрет удаления, ограничения и триггер                                  |
| `tests/routes.test.ts`      | Контракт HTTP-обработчиков с контролируемой границей Supabase: создание, повтор, конфликт ID, чужая запись, авторизация, отсутствие утечки SQL-ошибок |
| `tests/auth-errors.test.ts` | Различение почтовой квоты, ограничения получателей, недопустимого адреса и частоты запросов                                                           |

Тесты базы используют PGlite — PostgreSQL в локальном процессе. Тестовый адаптер создаёт минимальные `auth.users`, роли `anon`/`authenticated` и `auth.uid()` через настройку JWT subject. Политики и миграция выполняются настоящим PostgreSQL, а не проверкой SQL-строк. Это не тест сервиса Supabase Auth, PostgREST, обновления cookie или облачной инфраструктуры: их проверяет интеграционная коллекция.

Если среда Windows запрещает rename во временной папке, запустите тесты в обычном локальном терминале с разрешением на временные файлы. Отключать системную защиту не требуется.

## Импорт в Postman Desktop

Запуск JSON-коллекции через CLI не добавляет её автоматически в Desktop. 7 ноября коллекция **LD LATTE — API and Supabase RLS** импортирована в открытый Postman Desktop. У запросов тесты находятся в **Scripts → Post-response**; общие скрипты также заданы на уровне коллекции/папок. Результаты видны после отправки запроса или запуска коллекции через Runner.

Для будущих демонстрационных пользователей подготовлен локальный файл `postman/demo.local.postman_environment.json`: Supabase URL и публичный ключ заполнены, поля обоих email/паролей пустые. Его нужно импортировать через **Import** и выбрать справа сверху вместо окружения другого проекта. Не заполняйте чужое окружение `NestJS Local` данными этого приложения. Дополнение 7 ноября: в Postman Desktop наблюдён сохранённый Runner-прогон коллекции с 101 проверкой и 0 ошибок. У шести smoke-запросов видно по две успешные проверки. Это подтверждает наличие и выполнение скриптов в Desktop; новый прогон этим наблюдением не запускался. Для полного прогона с вашими новыми аккаунтами заполните четыре поля локально. Не запускайте интеграционную папку с пустыми адресами, если не хотите автоматически создать ещё два синтетических аккаунта.

Два личных аккаунта из повторного прогона удалены; старые значения окружения больше не подходят. `registered-users.local.json` очищен. Приватные окружения исключены из Git; не публикуйте их вместе с коллекцией.

В тестовом проекте подтверждение почты временно отключено пользователем. Штатная регистрация не отправляет письма. Если включить подтверждение обратно, для новых аккаунтов нужен доступ к письмам; ранее Auth Logs фиксировал `over_email_send_rate_limit`. План подключения — [SMTP.md](SMTP.md).

1. Запустите Next.js (`npm run dev`).
2. Импортируйте `postman/LD-LATTE.postman_collection.json` и `postman/local.postman_environment.json`.
3. Выберите импортированное окружение.
4. Укажите `base_url`, например `http://127.0.0.1:3000`.
5. Папку **00 Contract smoke** можно запускать без Supabase. Она проверяет 400/403/415 и коды ошибок до обращения к базе.
6. Для **01 Integration and RLS** заполните параметры ниже и запускайте папку целиком, по порядку, с одной итерацией. Включите поддержку cookie jar: проверка входа/выхода специально использует настоящие cookie.

## Параметры окружения

| Переменная              | Значение                                                           |
| ----------------------- | ------------------------------------------------------------------ |
| `base_url`              | URL Next.js, без завершающего `/`                                  |
| `supabase_url`          | URL того же проекта Supabase, который использует приложение        |
| `supabase_key`          | Publishable или legacy anon key; без service role                  |
| `email_domain`          | Домен тестовой почты для автоматически создаваемых пользователей   |
| `email_a`, `password_a` | Необязательно: существующий подтверждённый тестовый пользователь А |
| `email_b`, `password_b` | Необязательно: существующий подтверждённый тестовый пользователь Б |

Есть два режима:

1. **Новые пользователи.** Оставьте `email_a/email_b` пустыми, укажите подходящий тестовый домен. Коллекция создаст уникальные адреса, пароли, UUID и названия в run-local variables. В отдельном тестовом Supabase-проекте должен быть отключён Confirm email; в противном случае тест явно укажет на необходимость подтверждения и последующий вход не пройдёт.
2. **Существующие пользователи.** Укажите два разных подтверждённых адреса и их пароли. Запросы регистрации пропускаются. Подходит при включённом подтверждении почты и для повторных прогонов без создания новых аккаунтов. Создание аккаунта тогда проверяется вручную либо отдельным прогоном новых пользователей.

Не коммитьте окружение с паролями. Сохраните заполненную копию как `postman/private.local.json` (исключена из Git) и передавайте её CLI через `-e`. Исходный шаблон окружения оставляйте пустым. Токены/временные идентификаторы хранятся в `pm.variables` только на время одного прогона.

Коллекция создаёт две заявки за интеграционный прогон и, в первом режиме, два аккаунта. Удаления через пользовательский API в ТЗ нет; тест специально проверяет запрет DELETE. При необходимости очищайте только данные выделенного тестового проекта вручную от имени администратора. Не запускайте коллекцию на рабочих данных.

## Состав коллекции

Всего 50 запросов: 6 smoke + 44 интеграционных. Smoke-папка также проверяет, что запрос с Origin самого приложения проходит проверку источника и доходит до валидации полей.

| Группа сценариев     | Проверки                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| Аккаунт              | Регистрация, cookie-вход, сессия, выход, отсутствие сессии после выхода                            |
| JWT                  | Получение токенов А/Б в Supabase, отклонение неверного Bearer                                      |
| Создание             | `Новая`, правильный владелец, повтор с тем же UUID, конфликт изменённого запроса, отсутствие дубля |
| Чтение/изменение     | Повторное чтение, изменение полей и статуса, завершение                                            |
| Список               | Поиск, статус, совместная фильтрация, пустые результаты, неверная страница/статус                  |
| Валидация            | Пробельные обязательные поля, неизвестная категория, UUID, пустой PATCH, лишние поля               |
| Доступ через Next.js | Б не видит/не изменяет А, А не видит Б                                                             |
| Прямой Supabase REST | Своя строка доступна, чужая скрыта, чужой UPDATE меняет 0 строк                                    |
| Усиление прав        | Запрет подмены владельца, служебных дат, начального статуса, удаления                              |
| После атак           | Исходная заявка осталась неизменной                                                                |

Прямой PATCH чужой строки в PostgREST может успешно вернуть 200 с пустым массивом: это ожидаемое действие RLS — ни одна доступная строка не затронута. Коллекция проверяет именно пустой результат, а затем повторно читает заявку от имени владельца.

## Postman CLI

Установите CLI из [официальной инструкции Postman](https://learning.postman.com/docs/postman-cli/postman-cli-installation/), затем:

```powershell
postman collection run postman/LD-LATTE.postman_collection.json -e postman/private.local.json
postman collection run postman/LD-LATTE.postman_collection.json -e postman/local.postman_environment.json -i "00 Contract smoke" --no-report-events
```

CLI можно запускать с локальным файлом коллекции: [документация запуска](https://learning.postman.com/docs/postman-cli/postman-cli-run-collection). Скрипты npm используют пустой шаблон окружения; для полного прогона предпочтительна команда с приватной локальной копией.

Веб-проект не содержит Newman: аудит установленной версии 6.2.3 показал уязвимые транзитивные зависимости. Непроверенные overrides и откат на старую основную версию не применялись.

## Ручная приёмка по ТЗ

1. Зарегистрировать А, войти; проверить отказ при неверном пароле.
2. Создать заявку со всеми полями; новая заявка имеет статус `Новая`.
3. Открыть заявку, изменить название, описание, категорию и статус; результат виден после сохранения.
4. Проверить поиск отдельно, фильтр отдельно и их сочетание; проверить пустой результат.
5. Обновить страницу, выйти и войти заново: данные остались.
6. В другом профиле браузера войти как Б: список А недоступен. Выполнить также прямые REST-проверки из коллекции.
7. Проверить диалог с клавиатуры: фокус внутри, Escape закрывает с подтверждением при изменениях, при сохранении закрытие заблокировано.
8. На экране 390×844 и 360×800 проверить вход, список, длинное название, форму, поиск, фильтр и выход; горизонтальной прокрутки быть не должно.
9. При медленной сети быстро нажать сохранение несколько раз: создаётся одна заявка.
10. При потере сети проверить понятную ошибку, сохранность введённого текста и повторное сохранение с тем же ID.
11. Включить подтверждение почты в отдельном тестовом сценарии: сообщение о письме, подтверждение, последующий вход.
12. Проверить опубликованные ссылки и отсутствие секретов в репозитории.

Пункты, требующие реального Supabase и браузерной сессии, нельзя считать пройденными только на основании unit-тестов.
